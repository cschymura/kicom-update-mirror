## Executed implementation (not merely a plan)

Read original trusted KiCom 0.9.26 R3 DEV code: `DevAuthAdapter::verifyAndIssue` creates the DEV session only after a verified WebAuthn assertion, and `DevSession.php` persists that session's `auth_method` and `credential_id` server-side. Crucially, `authenticate` returns a DEV bearer context but does NOT return a trusted private-memory owner or the passkey's credential ID. Treat session label and a client-supplied subject as NON-AUTHORITY.

Four **new isolated DEV source modules** now bridge that gap:
- `KiComEngramDevSessionCredentialReader.php`: after genuine DEV session authentication, reads the actual protected KiCom DEV session JSON under its own existing shared lock (no creation of replacement lock), validates active passkey session, session ID, mode/private directory and expiry, and returns only internally the stored verified credential ID. It is NOT a token authenticator itself or a public endpoint.
- `KiComEngramVerifiedCredentialResolver.php`: maps SHA-256 of this credential ID via an independently provisioned, currently enabled private owner mapping to a stable subject, permitted namespaces and explicit `engram.read`/`engram.write` privileges; labels/session IDs/HTTP subject values are not owner identity. Fails closed on unknown/disabled mapping, malformed privileges or non-passkey issuance.
- `KiComEngramPrivateOwnerRegistry.php`: reads the explicitly provisioned fixed-name `engram-owners.json` from an existing 0700 non-web directory, requiring a non-symlink single-link 0600 regular file with strict size and JSON schema. Never creates a default owner, auto-enrolls, uploads real passkey data or grants privileges from user content. Provisioning and revocation must be handled by a trusted operator-authorized KiCom process; same-UID host isolation has NOT been proven live.
- The already-tested `KiComEngramDevMemoryAdapter.php` from DEV-22 now works in synthetic CI end-to-end with the above independent credential-to-owner resolution via the existing isolated `KiComEngramStore` and the consent-gated `KiComEngramAuthenticatedBridge`. An independently issued second KiCom DEV session using the same SYNTHETIC registered passkey retrieves the first session's stored SQLite engram. A different registered owner, unknown passkey, non-passkey session, revoked session, or unsafe registry cannot access it.

NEW reproducible synthetic suites:
- `test-engram-verified-credential-resolver.php`: 15 passed checks of a trusted passkey credential owner resolver and two-passkey same-owner read/write rights.
- `test-engram-dev-session-credential-reader.php`: 18 passed checks against REAL KiCom DEV session manager's protected synthetic JSON records and cross-session memory retrieval (not merely an invented identity callback).
- `test-engram-private-owner-registry.php`: 14 passed checks for actual non-web private operator registry, cross-session recall and directory/file/symlink and unknown-owner rejection.
All three are included in `test-engram.php` and the fixed-list, non-installable, code-only review archive. Original KiCom R3 source, production routing/kernel and host-probe-only 0.9.27 candidate are NOT mutated by this work.
