# KiCom Expansion/Federation — Orchestrator v1 checkpoint

Recorded: 2026-09-16
Status: candidate implementation, CI green

## What is now implemented

The Expansion/Federation candidate has moved beyond protocol-only work. The parent can now prepare a target-specific child-cell package and has a complete orchestration path for:

`prepare -> package -> FTPS/FTP deploy -> bootstrap probe -> enroll -> signed activate -> signed cron tick`

Implemented components:

- `ExpansionCellPackageBuilder.php`: builds a target-specific `/kicom/` child package with a one-time bootstrap configuration, runtime endpoints and a hash manifest.
- `ExpansionHttpTransport.php`: HTTPS-only, no-redirect, exact-child transport for parent/child JSON communication.
- `ExpansionOrchestrator.php`: one-shot parent workflow for prepare, deploy, enrollment, activation and first signed federation tick.
- `ExpansionParentIdentity.php`: persistent root/parent Ed25519 federation identity stored locally to the parent KiCom installation.
- `ExpansionService.php`: command facade intended to become the KiCom-facing expansion operation. FTP/FTPS credentials exist only for the duration of `execute()` and are not written to the registry or returned.
- Child runtime endpoints under `cell-runtime/`: `bootstrap.php`, `federation.php`, `status.php`, plus shared runtime code and `.htaccess` guards.
- The package builder also creates a `var/.htaccess` deny rule and destroys the transient target-specific package after a deployment attempt because it contains the one-time enrollment token.

## Child lifecycle

The uploaded child starts with a target-specific `bootstrap.config.php` generated by the parent. On the first valid bootstrap request the child:

1. creates its own Ed25519 identity locally;
2. stores its own private signing key locally;
3. moves enrollment material into its private runtime state;
4. removes the uploaded bootstrap configuration;
5. returns the descriptor + enrollment proof;
6. accepts only a signed parent activation envelope;
7. deletes remaining bootstrap enrollment material after activation;
8. accepts signed federation messages and returns signed replies.

The child does not receive the parent private key.

## Parent lifecycle

The parent owns a persistent federation identity and registry. A normal expansion command is intended to contain:

- target HTTPS base URL;
- remote web-root;
- temporary FTP/FTPS host, port, username and password;
- optional explicit plaintext-FTP opt-in.

FTPS is attempted first. Plain FTP is not used unless explicitly requested.

## Cron federation

After activation the parent sends a signed `FEDERATION_TICK`. The child verifies sender, receiver, timestamp, payload hash and signature, then returns a signed result. This establishes the path for the existing parent cron to fan out work to child cells without requiring a hosting-panel cron entry for every child.

## Shared-hosting compatibility

The child package is designed for ordinary PHP shared hosting. The root `.htaccess` intentionally avoids directives that are invalid in `.htaccess` context. Private runtime storage gets its own `Require all denied` file.
